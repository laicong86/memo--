## 2. 分层与依赖方向

```
models  ←  config  ←  ui_main  ←  main
   ↑         ↑          ↑          ↑
storage ─────┴──────────┤          │
theme   ────────────────┤          │
ui_detail ──────────────┘          │
session_watcher ← tray ────────────┘
```

- **`models.py` 是零依赖基础层**，不 import 任何 UI / Win32 模块。
- `config.py` 只依赖 `models`；`storage.py` 只依赖 `models`。
  → 保证 QA 在任何平台都能 `import models / storage / config` 写纯逻辑单元测试。
- `theme.py` 独立成文件，专门用来**打破 `ui_main` 与 `ui_detail` 的循环 import**。
- `tray.py` / `session_watcher.py` 顶层做 `sys.platform == "win32"` 判断：
  结构体只用 `ctypes` 基础类型定义（不使用 `ctypes.wintypes`），
  `ctypes.WINFUNCTYPE` 也做了条件化，因此非 Windows 下 import 不会抛异常。

## 3. 关键设计决策

### 3.1 零第三方依赖的托盘（ctypes 直调 Win32）
- 不用 `pywin32` / `pystray`：环境实测缺失且离线安装会失败。
- `RegisterClassExW` 注册窗口类，`CreateWindowExW(WS_OVERLAPPED)` 创建**不显示**的隐藏消息窗口。
  > 特意不用 `HWND_MESSAGE` 消息窗口，因为它收不到广播类会话通知；普通隐藏顶层窗口可正常接收 WTS 通知。
- `Shell_NotifyIconW` 位于 **`shell32.dll`**（不是 user32），
  用 `NIM_ADD / NIM_MODIFY / NIM_DELETE` 管理图标，`NIF_INFO` 弹气泡。
- 右键菜单用 `CreatePopupMenu + AppendMenuW + TrackPopupMenu(TPM_RETURNCMD)`，
  菜单项 ID：`ID_SHOW=1001` / `ID_NEW=1002` / `ID_EXIT=1003`。
- 图标用系统自带 `IDI_APPLICATION (32512)`，通过 `LoadIconW(NULL, MAKEINTRESOURCE(...))` 获取，
  不引入任何图标资源文件。

### 3.2 线程模型（关键）
tkinter 的 `mainloop()` 与 Win32 消息循环都绑定「线程消息队列」，不能简单共存。采用：

- **托盘消息循环跑在独立 daemon 线程**：`GetMessageW → TranslateMessage → DispatchMessageW`。
- 所有窗口过程回调（左键、右键菜单、解锁）通过注入的 `dispatcher(fn, args)`
  → 在 `main.py` 里用 `root.after(0, ...)` **投递回 tkinter 主线程**，
  绝不可以在托盘线程里直接操作 tkinter 控件。
- 主线程要弹气泡 / 退出时，不直接跨线程调 `Shell_NotifyIcon`，
  而是把文本放进 `queue.Queue` 并 `PostMessageW(hwnd, WM_APP_NOTIFY/WM_APP_QUIT, 0, 0)`，
  由托盘线程在窗口过程里执行，保证 API 调用与图标创建在同一线程。
- WNDPROC 回调对象被 `self._wnd_proc` 长期持有引用，防止被 GC 后回调崩溃。
- 所有 Windows 函数都显式声明 `argtypes / restype`，**64 位 Python 下避免指针截断**。

### 3.3 解锁屏幕提醒
- `wtsapi32.dll` 的 `WTSRegisterSessionNotification(hwnd, NOTIFY_FOR_THIS_SESSION)`。
- 窗口过程收到 `WM_WTSSESSION_CHANGE (0x02B1)` 且 `wParam == WTS_SESSION_UNLOCK (0x8)`
  → `SessionWatcher.handle_message()` 返回 True 并触发回调。
- `MemoApp.on_unlock()` 调 `store.count_pending()`，
  用托盘气泡提示「还有 N 条未完成事务」，同时刷新主窗口状态栏。
- 气泡由 `NOTIFYICONDATAW.szInfo / szInfoTitle / dwInfoFlags=NIIF_INFO` 实现；
  **未额外弹窗**，避免干扰用户。若系统勿扰模式折叠气泡，状态栏仍有同样文案。

### 3.4 圆角卡片窗口
- `overrideredirect(True)` 去掉系统边框；`attributes("-transparentcolor", #010203)` 把键色像素变透明。
- 全窗口铺一个 `Canvas`，用 `round_rect_points()` 采样四角四分之一圆生成多边形，
  绘制浅色圆角卡片；内容容器用 `create_window` 嵌入，随 `<Configure>` 调整尺寸。
- 顶部「圆角分隔弧线」用一个小 Canvas 画平滑曲线（`create_line(smooth=True)`）。
- 无边框窗口的拖动通过标题标签 / 顶部空白处绑定 `<ButtonPress-1> + <B1-Motion>` 实现。
- 详情面板展开时窗口宽度 `780 → 1180`，并自动向左偏移避免超出屏幕右边界。

### 3.5 事务列表采用 Canvas 自绘
用手绘 Canvas 而非 Treeview，以精确还原草图：每行的**彩色圆角标签**、
左侧标题、右侧「创建时间，预期完成时间」、行间横线。
- 命中检测：`index = (y + scroll * ROW_HEIGHT) // ROW_HEIGHT`（O(1)）。
- `<Double-Button-1>` → `show_detail(memo)`；`<MouseWheel>` 自维护行偏移滚动。
- 单行高度 `ROW_HEIGHT = 58`。

### 3.6 配色规则（可配置）
`config.classify_color_key(status, due_at, urgency, now, due_soon_hours)` 是**纯函数**，
便于 QA 直接测试，判定优先级：

```
已完成                  → done
已逾期 且 紧急=高       → overdue_high
已逾期                  → overdue
未逾期 且 紧急=高       → urgent_high
距到期 ≤ 临期阈值(48h)  → due_soon
其它                    → normal
```

`AppConfig` 把 `color_map / due_soon_hours / sort_mode` 持久化到 `data/config.json`，
「配色设置」窗口提供下拉预设 + 自定义 `#RRGGBB` + 色块预览 + 恢复默认。
颜色关系完全由用户选择，不写死在绘制逻辑里。

### 3.7 时间与数据
- 所有时间：`datetime.now()`（本机系统时间），**不 UTC、不硬编码**。
  统一格式 `%Y-%m-%d %H:%M:%S`，同时兼容 `YYYY-MM-DD`、斜杠分隔、省略秒等输入。
- `created_at` 在 `Memo.__init__` 里自动生成，UI 不提供输入框（只读展示）。
- 数据文件 `data/memos.json`，结构 `{"version":1, "memos":[...]}`；
  配置文件 `data/config.json`。
- `data_dir()` 源码运行时取脚本目录、打包后取 `sys.executable` 目录，
  并支持 `MEMO_DATA_DIR` 覆盖 —— 运行时数据不会写到工作区之外。
- 文件损坏 / 缺失时 `load()` 安全降级为空库，不抛异常。

### 3.8 排序
`sorted_by(mode, keyword)`：
- `created_at`：创建时间倒序（最新在前）；
- `due_at`：预期完成时间升序，未设置的用 `9999-12-31 23:59:59` 排最后；
- `urgency`：`高=0 / 中=1 / 低=2` 升序；
- 所有模式最后做一次**稳定排序**让「未完成」排在「已完成」之前。

## 4. 如何配置颜色

1. 图形界面：托盘 → 显示主窗口 → 点「配色设置」→ 为每个类别选颜色 / 填 `#RRGGBB`
   → 可同时改「临期阈值(小时)」「默认排序」→「保存设置」，列表颜色立即刷新。
2. 手工编辑 `data/config.json`（改完重启程序）。示例：

```json
{
  "version": 1,
  "color_map": {
    "done": "#9E9E9E",
    "overdue_high": "#D32F2F",
    "overdue": "#F57C00",
    "urgent_high": "#F9A825",
    "due_soon": "#FDD835",
    "normal": "#43A047"
  },
  "due_soon_hours": 48,
  "sort_mode": "created_at"
}
```

`sort_mode` 合法值：`created_at` / `due_at` / `urgency`。
非法颜色值会被忽略并回退到默认色，不会导致程序崩溃。

## 7. 已知限制

1. 圆角透明窗口在极个别 Windows 主题 / 远程桌面环境下可能退化为直角，功能不受影响。
2. 托盘使用系统默认图标（未内置 ico 资源）；如需自定义图标，可替换为
   `LoadImageW` 加载本地 `.ico` 并填入 `NOTIFYICONDATAW.hIcon`。
3. 托盘气泡可能被 Windows「专注助手 / 勿扰模式」折叠；状态栏提示作为兜底。
4. `overrideredirect` 窗口不出现在任务栏，符合「最小化到托盘」的产品预期；
   若托盘启动失败（非 Windows 或权限异常），程序会自动降级为直接显示窗口。
5. 进度记录目前为纯文本日志（含 `[进度 N%]` 前缀），未做图表化展示。
6. 数据为本地 JSON 单文件，未做多实例并发写锁；建议只运行一个实例。

## 8. QA 缺陷修复记录（回归轮）

QA 独立验证共 226 用例，首轮 223 通过 / 3 失败，判定 `ROUTE: engineer`。
本章记录 3 处源码缺陷的根因修复与回归结果。**未修改 `tests/` 下任何断言，
未修改 `docs/测试报告.md`，未改动其余 7 个源码文件。**

### FIND-001（中低：启动崩溃）
- **契约**：`storage.MemoStore.load()` docstring「文件异常时保持空库，不抛异常」。
- **根因**：JSON 中 `1e999` 被 `json.load` 解析为 `float('inf')`；
  `models.normalize_progress()` 的 `int(inf)` 抛 `OverflowError`，
  而原代码只捕获 `(TypeError, ValueError)`；`load()` 的 except 也未含
  `OverflowError`，异常冒泡到 `MemoApp` 启动链路导致程序无法启动。
- **修复（models.py）**：新增 `import math`；`normalize_progress()` 先用
  `math.isfinite()` 判定浮点，NaN / ±inf 一律回落到默认进度 `0`，
  并把 `OverflowError` 纳入 `int()` 的异常捕获。
- **修复（storage.py）**：`load()` 改为**逐条容错**（单条记录损坏只跳过该条，
  尽量保留其余可用数据）；except 扩展为
  `(OSError, ValueError, TypeError, OverflowError)`，并追加 `except Exception`
  兜底，保证任何损坏/非有限数值都不冒泡。
- **回归**：`normalize_progress(nan / +inf / -inf / 1e999) == 0`；原有行为保持
  （`3.9→3`、`True→1`、`"65"→65`、`250→100`、`"abc"→0`）；
  含 `1e999` 的文件可正常 load，坏记录进度回落为 0，同文件其它好记录仍可用。

### FIND-002（低：非法颜色可写入配置）
- **契约**：`config.is_valid_hex()` docstring「判断是否为合法的 #RRGGBB 颜色值」。
- **根因**：`int(text[1:], 16)` 过于宽松，接受 `#0x1234`、`# 12345`、`#+12345`；
  这些值可经 `ui_main._save_settings()` 写入 `config.json`，随后
  `draw_rows()` 把非法颜色交给 Tk 触发 `TclError`。
- **修复（config.py）**：新增 `import re`，改用
  `re.fullmatch(r"#[0-9A-Fa-f]{6}", text)`，严格只接受 6 位十六进制。
- **回归**：3 个可疑值全部拒绝；`#FFFFFF / #000000 / #abcdef / #AaBbCc` 全部接受；
  `DEFAULT_COLOR_MAP` 与 `COLOR_PRESETS` 全部合法；全部默认颜色可安全传给 Tk Canvas。

### FIND-003（低-中：斜杠日期排序错误）
- **契约**：`storage.sorted_by("due_at")` docstring「预期完成时间升序（越早到期越靠前，
  未设置的排最后）」。
- **根因**：按 `due_at` **原始字符串**排序，`"2024/12/1" < "2024/6/1"`；
  而 `models.parse_time()` 与 `config.classify_color_key()` 都按**真实时间**判定，
  排序与配色两处时间语义不一致。
- **修复（storage.py）**：新增 `from datetime import datetime`，删除不再使用的
  `_FAR_FUTURE` 字符串常量；排序键改为
  `(m.due_datetime() or datetime.max, m.created_at)`，
  未设置 / 解析失败用 `datetime.max` 置于末尾。
- **回归**：`2024/6/1` 排在 `2024/12/1` 之前；标准格式、斜杠格式、未设置、
  非法文本混排结果为 `std(3月) → june(6月) → dec(12月) → unset → bad`，
  与配色判定的时间语义完全一致。

## 9. FIND-004 同源遗漏修复记录（交付前最后一轮）

QA 回归轮后的独立探测发现：上一轮修复覆盖了 `models` / `storage` 分支，
但**未覆盖 `config` 分支的同一根因** —— `config.json` 中的 `1e999`（→ `inf`）
仍会让启动崩溃。本轮做最后一次定点加固，**只改 `config.py` 与本文档**。

### 缺陷链路
`json.load` 把 `1e999` 解析为 `float('inf')` → `AppConfig.load` →
`apply_dict`（`due_soon_hours`）→ `_safe_hours(inf)` → `int(inf)` 抛
`OverflowError`；而 `_safe_hours` 只捕获 `(TypeError, ValueError)`、
`AppConfig.load` 的 except 也未含 `OverflowError` → 冒泡到
`MemoApp.__init__`（位于 `tk.Tk()` 之前且无 try/except）→ 启动失败。
`classify_color_key` 直接传 `due_soon_hours=inf` 时同样抛异常。

### 修复点（config.py）
1. **`_coerce_hours(value, default)`（新增）**：统一的有限整数规整原语。
   先用 `math.isfinite()` 判定浮点，NaN / ±inf 一律返回 `default`；
   `int()` 的异常捕获扩为 `(TypeError, ValueError, OverflowError)`；
   合法范围仍为 `1..24*365`（常量 `_MAX_HOURS`）。
2. **`_safe_hours(value, fallback)`**：不再自行做转换，改为先用
   `_coerce_hours(fallback, DEFAULT_DUE_SOON_HOURS)` 规整 fallback，
   再用 `_coerce_hours(value, safe_fallback)` 规整输入 ——
   **value 与 fallback 双重免疫**，返回值永远是安全有限整数。
   与 `models.normalize_progress` 采用同一 `math.isfinite` 通用规则，
   未硬编码 `1e999` 或任何测试数据。
3. **`AppConfig.load`**：except 扩为
   `(OSError, ValueError, TypeError, OverflowError)`，并追加
   `except Exception` 兜底；两个分支都**重建 `cfg = cls(path=path)`**，
   严格兑现 docstring「缺失或损坏时返回默认配置」，不残留部分应用结果，
   与 `storage.MemoStore.load` 的兜底策略对齐。
4. **同源自查加固（config.py 内其余转换/成员判断点）**：
   - `__init__` / `apply_dict` 的 `sort_mode in SORT_MODE_LABELS` 前置
     `isinstance(mode, str)`，避免 list/dict 等不可哈希值抛 `TypeError`；
   - `get_color` / `set_color` 前置 `isinstance(key, str)`；
   - `classify_color_key` 的 `due_at` 前置 `isinstance(due_at, str)`，
     非字符串按「未设置」处理；`hours = _safe_hours(due_soon_hours)`
     在修完第 1/2 点后自动免疫，`float(hours)` 只接收安全整数；
   - `is_valid_hex` 使用 `re.fullmatch`，无任何 `int()` 转换。
   - 全文件仅剩 `_coerce_hours` 一处 `int()`，已被完整防护；
     已用 Grep 逐行核对所有 `int() / float() / 成员判断` 点，无遗漏。
5. **合法值行为不变**：`24 → 24`、`"24" → 24`、`1 → 1`、`8760 → 8760`；
   `_safe_hours(0, 99) → 99`、`_safe_hours(10**9, 7) → 7` 等既有边界断言保持。

## 16. 光标拖动残留修复（第二轮，真正根因）（2026-11-16）

### 反馈
上一轮删除常驻 `cursor="fleur"` 后，鼠标移入窗口仍显示拖动（调整大小）光标。

### 真正根因
1. 鼠标从窗口外进入时先穿过边缘 8px 热区，Canvas 的 `<Motion>` 把光标设为
   方向箭头（如 `right_side`）；
2. 指针继续移入内部后，事件落在 `container` 及其子控件上——这些控件的
   `cursor` 是空字符串，而 **Tk 空光标会继承父级**，于是继承了 Canvas 上
   的调整光标；
3. 此时指针不再悬于 Canvas，Canvas 的 `<Motion>` 不再触发，光标永远
   无法复位 → 整个窗口看起来都是拖动箭头。

### 修复（ui_main.py）
- 改用 `self.root.bind_all("<Motion>", self._on_any_motion, add="+")`
  全局监听，任何控件上的移动都会触发；
- `_on_any_motion` 用 `winfo_pointerx/pointery - canvas.winfo_rootx/rooty`
  把指针换算成 Canvas 坐标（事件坐标是相对悬停控件的，不能直接用），
  再调 `_apply_cursor_for`；
- `_apply_cursor_for`：在边缘热区 → 设置对应方向光标；离开热区 →
  Canvas 光标复位为 `""`（普通箭头）。只清 Canvas，有自己光标的控件
  （按钮 hand2、输入框 xterm）不受影响；
- 拖拽调整大小期间（`_resizing`）跳过复位，避免抖动。

### 验证
真实窗口（780×560）：
```

右边缘热区   → cursor = 'right_side'
回到中心     → cursor = ''        （立即复位）
bind_all Motion 已注册
全窗口遍历   → 无任何 fleur 残留
```
- 全量回归 **`Ran 290 tests / OK`**。
